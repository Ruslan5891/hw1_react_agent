# ReAct-агент для спортивних розрахунків (біг і тренування)

## 1. Опис проєкту

ReAct-агент на LangGraph, який відповідає на запитання тих, хто займається бігом: рахує темп і швидкість, прогнозує час на іншій дистанції, визначає пульсові зони та оцінює витрату калорій. Агент працює в циклі LLM – tools – LLM: модель вирішує, який інструмент викликати, отримує результат і або робить наступний виклик, або формує відповідь. Фінальна відповідь повертається у структурованому вигляді (`answer`, `confidence`, `sources`). Агент захищений лімітом кроків, тайм-аутом і детектором зациклення, а кожен запуск записується у JSON-траєкторію.

LLM — модель OpenAI `gpt-4o-mini`, підключена через `ChatOpenAI` з LangChain. Запити йдуть через шлюз OpenRouter (`base_url="https://openrouter.ai/api/v1"`), а не напряму в OpenAI API.

## 2. Доменна задача

- **Домен:** спорт — тренування з бігу та загальна фізична активність.
- **Що вирішує агент:** запити на кшталт «який у мене був темп?», «за скільки я пробіжу півмарафон?», «які в мене пульсові зони?», «скільки калорій я спалю?», а також складені запити, де один розрахунок залежить від іншого.
- **Інструменти (tools):**
  - `calculate_pace` — темп (хв/км) і швидкість (км/год) за дистанцією та часом;
  - `predict_race_time` — прогноз часу на іншій дистанції за формулою Рігеля;
  - `calculate_heart_rate_zones` — максимальний пульс і п'ять пульсових зон (метод Карвонена, якщо відомий пульс у спокої);
  - `estimate_calories` — витрата калорій за видом активності, вагою та тривалістю (метод MET).

Усі інструменти — це формули, а не звернення до зовнішніх API, тому їхні результати детерміновані, і їх легко перевірити вручну.

Кожен інструмент має Pydantic v2 схему: `Field(description=...)` для кожного параметра, `field_validator` для перевірки й нормалізації, закриту схему (`extra="forbid"`) і docstring з поясненням, коли інструмент застосовувати. Два інструменти додатково мають `model_validator` для правил між полями.

## 3. Архітектура

```
START → agent ──(є tool_calls)──────→ tools ──→ agent   (цикл)
          │
          ├──(фінальна відповідь)───→ formatter ──────→ END
          └──(спрацював захист)─────→ guard_finalize ─→ END
```

- **agent** — LLM з `bind_tools`. Перед викликом LLM перевіряє ліміт кроків і тайм-аут, після відповіді — тайм-аут і зациклення (до виконання інструментів).
- **tools** — `ToolNode` з LangGraph. Помилки інструментів (зокрема `ValidationError`) не обвалюють граф, а повертаються моделі як `ToolMessage` зі статусом `error`.
- **conditional edge** (`route_after_agent`) — обирає `tools`, `formatter` або `guard_finalize`.
- **formatter** — `with_structured_output(FinalAnswer)` перетворює відповідь на Pydantic-модель з полями `answer`, `confidence`, `sources`.
- **guard_finalize** — формує часткову відповідь після спрацювання захисту. LLM тут не викликається: ліміт уже вичерпано, тому відповідь збирається з результатів, які агент встиг отримати.

Захисні механізми (`safety.py`):

| Механізм | Значення за замовчуванням | Де перевіряється | Що відбувається |
|---|---|---|---|
| `max_steps` | 10 ітерацій | перед кожним викликом LLM | цикл зупиняється, повертається часткова відповідь |
| `timeout` | 60 с (`time.monotonic()`) | перед викликом LLM і перед виконанням інструментів | те саме, нові інструменти не запускаються |
| `LoopDetector` | `max_repeats = 3` | після відповіді LLM | третій однаковий виклик поспіль блокується до виконання |

Окремо для кожного HTTP-запиту до LLM встановлено тайм-аут 30 с.

## 4. Інструкція запуску

1. Клонувати репозиторій: `git clone https://github.com/Ruslan5891/hw1_react_agent.git`.
2. Перейти в директорію: `cd hw1_react_agent`.
3. Створити оточення та встановити залежності:
   ```bash
   python3 -m venv .venv
   source .venv/bin/activate
   pip install -r requirements.txt
   ```
4. Налаштувати API-ключ: скопіювати `.env.example` у `.env` і вписати ключ OpenRouter у `OPENROUTER_API_KEY`.
5. Запустити:

| Команда | Що робить | Потрібен ключ |
|---|---|---|
| `python tools.py` | демонстрація інструментів: успішні виклики та відхилені валідацією | ні |
| `python agent.py` | три приклади роботи агента | так |
| `python test_runner.py` | п'ять тест-кейсів → `test_results.json`, `trajectory.json` | так |
| `python safety.py` | демонстрація max_steps, timeout, зациклення → три запуски `DEMO-*` у `trajectory.json` | так |

## 5. Результати тестування

Підсумкова таблиця за `test_results.json` (один прогін, `gpt-4o-mini`, ліміти: 10 кроків, 60 с):

| Test ID | Складність | Кроків | Tool calls | Час, мс | Статус |
|---|---|---|---|---|---|
| TC-001 | simple | 2 | calculate_pace × 1 | 3480 | ✅ success |
| TC-002 | medium | 2 | calculate_pace × 2 | 5017 | ✅ success |
| TC-003 | complex | 3 | predict_race_time, calculate_heart_rate_zones, calculate_pace, estimate_calories | 10997 | ✅ success |
| TC-004 | medium | 2 | calculate_heart_rate_zones × 1 (помилка валідації) | 4529 | ✅ success |
| TC-005 | edge | 2 | calculate_pace × 1 | 3578 | ⚠️ partial |

«Кроків» — кількість ітерацій циклу, тобто викликів LLM у вузлі `agent`. Статус визначається автоматично: `success` — агент завершив роботу сам, викликав очікувані інструменти, і відповідь містить очікувані факти; `partial` — одна з перевірок не пройдена (деталі в полі `checks`).

Демонстрація захисних механізмів (`python safety.py`, запуски `DEMO-max-steps`, `DEMO-timeout`, `DEMO-loop` у `trajectory.json`):

| Сценарій | Налаштування | Результат |
|---|---|---|
| max_steps | `max_steps=1`, справжня LLM, запит на два залежні розрахунки | зупинка після 1 кроку; часткова відповідь містить прогноз часу (1:50:19), калорії порахувати не встиг |
| timeout | `timeout=2 с`, справжня LLM, інструмент навмисно відповідає 3 с | зупинка з причиною `timeout` на 4.1 с; результат інструмента збережено у частковій відповіді |
| loop | `max_repeats=3`, сценарна модель повторює той самий виклик | третій виклик заблоковано до виконання; виконано 2 з 3 |

Зациклення показано на сценарній моделі (`ScriptedChatModel` у `safety.py`), бо справжня LLM не зациклюється на замовлення.

## 6. Аналіз результатів

**Чи правильно агент обирав tools?**

У чотирьох тест-кейсах з п'яти — так. У TC-001 агент викликав `calculate_pace` з точними аргументами користувача. У TC-002 він за одну відповідь LLM запросив два паралельні виклики `calculate_pace` (для себе і для друга) й сам порахував різницю 30 с/км. У TC-003 агент правильно врахував залежність між кроками: `estimate_calories` викликано лише на другій ітерації, коли прогнозований час уже був відомий. У TC-004 агент передав некоректний пульс в інструмент, отримав помилку валідації й пояснив її користувачу, не вигадуючи зон.

Неправильний вибір аргументів був у TC-005 і частково у TC-003 — про це нижче.

**Де агент помилявся і чому?**

1. **TC-005: модель мовчки «виправила» дані користувача.** На запит «пробіг півмарафон за 1:75:00» агент викликав `calculate_pace(time="1:15:00")` і впевнено (`confidence = 0.9`) відповів, що темп 3:33 хв/км. Валідатор відхилив би `1:75:00`, але до інструмента дійшло вже змінене значення, тому Pydantic тут не допоміг. У системний промпт додано правило «передавай значення користувача дослівно», проте поведінку воно не змінило. Це підтверджує тезу з курсу: текстове обмеження в промпті — не захист. Надійним виправленням була б перевірка в коді, що аргументи інструмента справді присутні в запиті користувача.
2. **TC-003: виклик із вигаданим аргументом.** На першій ітерації модель разом із `predict_race_time` паралельно викликала `calculate_pace(time="1:45:00")`, хоча прогнозований час ще не був відомий. Результат цього виклику (4:59 хв/км) у фінальну відповідь не потрапив: агент узяв правильний темп 5:14 з `predict_race_time`. Відповідь правильна, але один виклик зайвий.
3. **TC-003: округлення параметра.** Інструмент повернув тривалість 110.3 хв, а модель передала в `estimate_calories` значення 110. Тому калорій вийшло 1348 замість 1351 (різниця 0.2%).
4. **Поле `sources` не можна довіряти моделі.** Під час першого прогону formatter повернув для TC-002 порожній список, хоча інструменти викликалися. Тепер `sources` заповнюється з фактичної історії викликів. Зворотний бік: у TC-003 до `sources` потрапив і `calculate_pace`, результат якого у відповіді не використано.
5. **Поле `confidence` — самооцінка моделі.** У TC-005 воно дорівнює 0.9 для неправильної відповіді, тому покладатися на нього як на показник якості не можна.

Ще одну проблему знайдено в самому `ToolNode`: стандартний обробник помилок губить текст помилок `model_validator`, і модель отримувала порожнє повідомлення. Додано власний обробник `format_tool_error`, який передає текст усіх помилок.

**Кроки: simple vs complex.**

Прості й середні запити потребують 2 кроків (виклик інструмента + відповідь), складний — 3. Залежність не лінійна від кількості інструментів: у TC-002 два виклики, а у TC-003 чотири, але кроків лише на один більше, бо незалежні виклики модель робить паралельно. Кількість кроків визначається не кількістю інструментів, а глибиною залежностей між ними.

**Чи досягав агент max_steps або timeout?**

У п'яти тест-кейсах — ні: максимум 3 кроки з 10 дозволених і 11.0 с із 60. Запас великий, тому ліміти не впливали на результат. Спрацювання показано окремо командою `python safety.py` (таблиця вище). У демо тайм-ауту зупинка сталася на 4.1 с за ліміту 2 с: перевірка виконується між кроками і не перериває інструмент, який уже працює.

**Залежність часу виконання від складності.**

Двокрокові запити займають 3.5–5.0 с, складний — 11.0 с. Самі інструменти виконуються за частки мілісекунди, увесь час іде на виклики LLM. Час зростає і через додаткову ітерацію, і через довшу фінальну відповідь: у TC-003 останній виклик LLM тривав 3.7 с. Приблизно третину загального часу (33–40%) займає вузол `formatter` — це плата за окремий виклик для структурованої відповіді. Заміри зроблено за один прогін, тому числа мають похибку.

**Випадки, коли агент НЕ використав tool, хоч мав би.**

У п'яти тест-кейсах таких випадків немає. Під час розробки я спостерігав такий випадок поза `test_results.json`: на запит «Порахуй пульсові зони для людини віком 150 років з пульсом у спокої 60» агент відмовив без виклику інструмента, пославшись на межі 10–100 років. Ці межі він узяв з `Field(description=...)`. Відповідь правильна, але правило «не відмовляй без виклику інструмента» порушено. Отже, описи полів модель читає і використовує, а валідацію в коді вони не замінюють: у TC-004, де межа не очевидна з контексту запиту, модель виклик зробила й отримала помилку.

Перевірити можна командою:

```bash
python -c "from agent import run_agent, print_result; print_result(run_agent('Порахуй пульсові зони для людини віком 150 років з пульсом у спокої 60.'))"
```

## 7. Висновки та обмеження

- **Що працює добре:** вибір інструмента, паралельні виклики, залежні розрахунки, обробка помилок валідації, зупинка за всіма трьома захисними механізмами, часткова відповідь замість збою.
- **Що можна покращити:**
  - перевіряти в коді, що аргументи інструментів узято із запиту користувача (закрило б помилку TC-005);
  - об'єднати фінальну відповідь і форматування в один виклик LLM, щоб скоротити час приблизно на третину;
  - рахувати `confidence` за фактами траєкторії (помилки інструментів, спрацювання захисту), а не довіряти самооцінці моделі.
- **Відомі обмеження:**
  - тайм-аут кооперативний: перевіряється між кроками й не перериває виклик LLM чи інструмента, що вже виконується;
  - `max_steps` рахує ітерації циклу; виклик у вузлі `formatter` до ліміту не входить;
  - `LoopDetector` ловить лише однакові виклики поспіль, чергування двох викликів (A-B-A-B) він не помітить — такий випадок зупинить `max_steps`;
  - формули наближені: максимальний пульс 220 − вік, усереднені значення MET, формула Рігеля;
  - кожен тест-кейс запущено один раз; відповіді LLM не повністю відтворювані навіть за `temperature=0`.

## 8. Структура файлів

- `tools.py` — Pydantic-схеми та чотири інструменти (Завдання 1)
- `agent.py` — LangGraph граф, structured output, запуск агента (Завдання 2)
- `safety.py` — `SafetyConfig`, `LoopDetector`, `SafetyGuard`: max_steps, timeout, зациклення, а також демонстрація цих механізмів (Завдання 3)
- `logger.py` — `TrajectoryLogger` (Завдання 3)
- `test_runner.py` — тест-кейси та збір результатів (Завдання 4)
- `trajectory.json` — траєкторії п'яти тест-кейсів і трьох демо-запусків захисту (генерується)
- `test_results.json` — результати тестів (генерується)
- `requirements.txt` — залежності
- `.env.example` — зразок файлу з API-ключем
